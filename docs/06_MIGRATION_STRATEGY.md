# 06 — Migration Strategy (Supabase/PostgreSQL → PHP/MySQL)

## 0. Ground rules (binding)

1. **Production is never touched during development.** No connection to the live Supabase project, no Vercel changes, no DNS changes, no edge-function deploys, no migrations applied there. Nothing in this repo contains or asks for live credentials.
2. **We have no production export.** Everything below is *tooling and a procedure*. Until the owner supplies an authorized export, **no claim of data migration, account continuity or zero loss can be made** — the importer is tested only against synthetic fixtures generated by `backend/tools/make_fixture.php` (clearly marked `FIXTURE`, never resembling real people).
3. **Read-only against the source.** Source access is by owner-produced files (NDJSON/CSV from `psql \copy` / dashboard export) or, optionally, a dedicated read-only database role the owner creates. The importer never writes to the source.
4. **The importer is repeatable, resumable and idempotent** (`INSERT … ON DUPLICATE KEY UPDATE` keyed on preserved source UUIDs; `migration_runs` / `migration_row_map` tables).
5. **A zero-loss claim is only ever made by the reconciliation report**, never by the absence of errors.

Rows that violate target constraints are **quarantined** into `migration_rejects` with reason (never dropped silently) and make the reconciliation fail until resolved or explicitly waived by the owner.

## 3. Account continuity design

**Fact (to be verified with a real export, not assumed):** Supabase GoTrue stores passwords as **bcrypt** (`$2a$10$…`) in `auth.users.encrypted_password`. PHP's `password_verify()` verifies `$2a$/$2b$/$2y$` bcrypt, so existing users *should* be able to sign in with their current password without anyone knowing or resetting it.

Flow ("verify-then-upgrade"):
1. `users.password_hash` NULL, `legacy_bcrypt_hash` set.
2. On login, if `password_hash` is NULL: `password_verify($pw, $legacy)` → on success store `password_hash = password_hash($pw, PASSWORD_ARGON2ID or PASSWORD_BCRYPT cost 12)`, **null out `legacy_bcrypt_hash`**, issue session. Same rate limiting/lockout as normal login. Constant-time behaviour; dummy verify for unknown e-mails.
3. If verification fails for a user who *does* have a legacy hash → ordinary "invalid credentials" (no hint).
4. **Fallback (if hashes unusable/incompatible, or user prefers):** "Set your password" e-mail flow: single-use, hashed token, 60 min, available from the login screen (`forgot-password`); can also be bulk-triggered per cohort by the owner as a communication campaign. No weakening of password rules to make this easier.
5. Users with `email_confirmed_at` keep verified status; unverified remain unverified.
6. `phone` kept; phone verification capability depends on G-10.
7. OAuth/social identities: **none used by the app** (only `signInWithPassword`); `auth.identities` is not required. If P4 shows non-email identities, those users use the reset flow.
8. After **N=90 days** a scheduled job nulls any remaining `legacy_bcrypt_hash`; those users use the reset flow.
9. Existing JWTs/sessions are invalid after cutover → everyone signs in once; Next.js and Flutter show a calm "please sign in again" screen.
10. Cutover communication draft is included in `docs/runbooks/cutover.md` (Phase 8).

**Not done and not promised:** importing GoTrue refresh tokens, TOTP/MFA factors (none observed in code), magic-link continuity.

## 4. Controlled cutover (no dual-writing)

```
T-14d  Rehearsal #1 (staging MySQL + export copy) → reconciliation report reviewed
T-7d   Rehearsal #2 with fresh export; timings measured; rollback rehearsed
T-1d   Freeze deployments of web app; announce maintenance window (owner approves)
T0     1. Owner puts the existing app in read-only maintenance (banner + RLS/INSERT block — owner-executed, outside this repo)
       2. Final authorized export (full, not incremental) taken
       3. Importer full run into EMPTY production MySQL (or delta onto the T-7d baseline — see below)
       4. Reconciliation (see §5) must PASS; owner signs the report
       5. Smoke tests against PHP API (login legacy user, dashboard figures vs report, create sale in test business, webhook sandbox)
       6. Switch: Next.js env points to PHP API (Vercel env change — owner-executed), Flutter builds released to stores
       7. Monitor (error rate, login failures, webhook failures) for 72 h; Supabase kept intact, read-only, ≥ 30 days
Rollback: before step 6 → simply discard MySQL and re-open the old app. After step 6 and before new writes matter → flip env back; any sales created on PHP in the window are exported (reverse report) for manual re-entry/ reconciliation. After the point of no return (defined by the owner, default T+7d) rollback = restore from MySQL backups, not back to Supabase.
```
**Delta strategy before T0 (optional, reduces window):** baseline import from an export at T-7d; at T0 a second export is imported as an **upsert delta**. Change detection by watermark: `updated_at > baseline` for mutable tables, `created_at > baseline` for append-only tables (`sale_items`, `debt_repayments`, `loyalty_ledger`, `sale_edits`, `billing_history`). **Watermarks cannot see deletes**, so the T0 pass always compares the *full set of primary keys* per table (source id list vs target) and reports/ applies deletions as soft-deletes. Because a sale's `updated_at` changes on edit/repayment and its `sale_items` are replaced on edit (017 deletes & re-inserts items), the importer re-imports **whole sale aggregates** (sale + items + repayments + edits) for any sale touched since the baseline. We do **not** claim row-level CDC; logical replication from Supabase is not usable from shared hosting and is out of scope.

## 5. Validation & reconciliation (the only source of truth about success)

Automated report (`backend/migration/reconcile.php`) producing a signed JSON + HTML artefact:

1. **Row counts** per table: source (from export manifest with counts + SHA-256 per file) vs imported vs quarantined. Must satisfy `source = imported + quarantined(waived)`.
2. **Referential integrity** (every FK resolves; orphan list).
3. **Financial reconciliation per business and overall:** Σ`sales.total_amount`, Σ`subtotal`, Σ`tax`, Σ`discount`, Σ`amount_paid` by `payment_status`; Σ`sale_items.total_price` vs Σ`sales.subtotal` (reports the same ±0.01 anomalies that `edit_sale` refuses on); Σ`debt_repayments`; **open credit balance per customer**; Σ`expenses.amount`; Σ`billing_history.amount` by currency; PO totals; customers' `total_spent` / loyalty balance vs Σ ledger.
4. **Stock:** Σ`products.stock_quantity` equals Σ seeded `stock_levels`; per-product match.
5. **Profit parity:** run the PHP profit service and the original `computeProfit` (via a Node harness fed the same exported rows) for every business × {last 12 months}; **must agree to the cent**.
6. **Duplicate detection:** duplicate emails (case-insensitive), duplicate `(business, receipt_number)`, duplicate barcodes/SKUs, duplicate customers by phone — reported, not auto-merged.
7. **Auth:** count of users with usable legacy hash / without; verified-email parity.
8. **Sampling:** N random sales rendered through the document builder and compared field-by-field with source.
9. Logs never contain passwords, hashes, tokens, full emails beyond masked form (`a***@d***.com`), or customer PII beyond ids.

## 6. Tooling layout (Phase 8 deliverable)

`backend/migration/` — `Manifest`, `Reader` (NDJSON/CSV streaming), `Mapper` per table, `Importer` (chunked transactions, resumable by `migration_runs.offset`), `Reconciler`, `Quarantine`, `Report`; CLI: `php bin/migrate.php plan|dry-run|import|delta|reconcile|rollback --run=<id>`. `rollback` deletes rows tagged with the run id (every imported row carries `migration_run_id` in a side table), never touching rows created after cutover by users.

## 7. What can honestly be tested now

Mapper/reconciler unit tests on synthetic fixtures shaped from the migrations; Node-vs-PHP profit/edit-sale/loyalty golden parity tests (no data needed); legacy-bcrypt login transition using a **locally generated** `$2a$10$` hash (proves PHP compatibility with that format, *not* that real hashes will behave identically). These will be labelled in test output as fixture-based.
